# v0.5 Dogfood Fleet Sprint

Status: targeted execution plan

Date: 2026-08-29

Outcome: a signed v0.5 Windows release exercised as a small private fleet

## 1. Objective

Ship v0.5 as a trustworthy standalone Windows indexer that can also run as a
small, explicitly enrolled dogfood fleet. The release must install the core
product and, when requested through an advanced setup option, the observatory
collector. Several installations must retain complete local operation while
replicating into one manually configured central Eidos service.

This sprint is intentionally a real vertical slice rather than a mock fleet.
It puts the existing synchronization protocol and source ledger behind real
catalog, storage, authentication, and transport adapters early enough for the
collector and product telemetry to test the architecture. It does not attempt
to finish the broader v1 control plane.

The sprint ends with a signed `v0.5.0` release, not merely merged code or an
installer artifact.

## 2. Why this belongs before the broader rollout

The simulation-first sequence has paid for the protocol invariants that are
hardest to recover later: source epochs, rewind fencing, materialize-at-ship,
ACK-after-durable-commit, acknowledgement-gated retention, and Merkle repair.
The catalog now records source touches in the transactions that change the
source. The remaining uncertainty is concentrated at the production seams:

- materializing a consistent batch from a busy SQLite catalog;
- authenticating and reconnecting real machines in both directions;
- applying remote sources into the central catalog and search projection;
- bounding backlog, write amplification, and catch-up cost on intermittently
  connected machines;
- preserving identity through reinstall, restore, and journal replacement;
- deciding whether the planned batching and content-chunking approaches fit
  the measured edits and storage shapes; and
- separating the cost of Eidos from the cost of observing Eidos.

Deploying several disconnected standalone services would measure scanning and
indexing, but it would not exercise those risks. The private fleet is the least
expensive place to learn that the design is wrong.

## 3. Release topology

The smallest valid installation remains standalone. Enrollment adds a central
consumer without replacing local behavior.

```text
                       manual central (this host)
                  catalog + projection + global search
                         ^                 ^
                         | authenticated   |
                         | sync sessions   |
              either peer may initiate a connection
                         |                 |
             +-----------+----+       +----+-----------+
             | Windows node A |       | Windows node B |
             | local catalog  |       | local catalog  |
             | local search   |       | local search   |
             | durable ledger |       | durable ledger |
             | collector*     |       | collector*     |
             +----------------+       +----------------+

             * optional, separate LocalSystem service
```

Each node continues to scan, index, and answer local queries when central is
absent. Central retains the last durably applied state of an offline source and
reports its freshness. Central is not allowed to become a prerequisite for a
node's local readiness, catalog publication, content work, or shutdown.

Central is not a separate product edition. It is the same Eidos installation
with the central role enabled, and it may index and search its own local sources
alongside replicated sources. Running central on this host must not require a
second core service or surrender this host's local fallback.

## 4. Product and packaging decisions

### 4.1 One setup experience, two runtime boundaries

`eidos-setup.exe` becomes the authoritative installer. Its advanced options
include:

> **Install profiling collector**
>
> Runs a separate privileged service alongside Eidos and records bounded,
> privacy-preserving workload measurements.

The setup may chain separate core and collector MSIs internally. The services,
data directories, identities, ACLs, failure recovery, and uninstall semantics
remain separate:

- `eidos` owns indexing, local search, the web/API surface, and fleet sync;
- `eidos-collector` owns observation and remains a LocalSystem service;
- removing or disabling the collector cannot stop or reconfigure the core;
- removing the core cannot silently delete collector data; and
- upgrading either service must preserve its data and identity.

Selecting the collector may elevate an otherwise per-user core installation.
The UI must say so before Windows asks for approval. On maintenance and upgrade,
the checkbox reflects the installed collector state; an unchecked default must
not accidentally remove an existing collector. Explicit collector removal
preserves its study data unless the operator separately requests a purge.

Bare MSIs may remain as administrator and CI artifacts, but the unified setup
is the only primary v0.5 download.

### 4.2 Approved joining is the sync opt-in

Standalone installations do no fleet work. They do not maintain a fleet
backlog, accept sync connections, or transfer catalog data.

Joining is an explicit node-level action that selects an advertised master or
names its IP address. The master operator must approve the resulting node
notification. Once joined:

- all eligible local sources synchronize by default;
- a source may be marked `local_only` as an advanced exclusion;
- newly added eligible sources inherit the joined default;
- synchronization is continuous rather than enabled per operation;
- pausing synchronization stops transfer but preserves local indexes and durable
  state needed for a safe later resume; and
- leaving or retiring a node is distinct from temporarily disabling sync.

The existing per-source enable operation remains an internal epoch/backfill
mechanism. It is not the ordinary setup experience for this private fleet.

Master selection and approval are available in both the CLI and the Nodes UI.
LAN discovery is best-effort; entering the master's IP address is the reliable
fallback.

## 5. Synchronization slice

### 5.1 Real adapters around the existing state machines

The production path must use the ordering and durability semantics already
defined by `eidos-sync`; it must not implement a second protocol beside them.

Source side:

1. Read the source epoch, head sequence, consumer cursor, and materialized row
   images from one consistent catalog snapshot.
2. Form a bounded, versioned offer carrying the history-chain proof already
   required by the protocol.
3. Persist connection-independent peer progress; a broken socket loses no
   durable state.
4. Compact tombstones only through the oldest durably acknowledged consumer.

Central side:

1. Authenticate the node and bind the credential to its stable node identity.
2. Fence invalid epochs, rewinds, gaps, and incompatible row-image versions.
3. Apply replicated effects and the source watermark in the same SQLite
   transaction.
4. Emit an acknowledgement only after that transaction is durable.
5. Feed committed remote rows through the ordinary projection/search path.
6. Preserve the last applied source state while the node is offline and expose
   truthful coverage and freshness.

Metadata replication is required for release. Central results must carry host,
source, freshness, and completeness context and must not collapse distinct
source identities that happen to expose the same path.

### 5.2 Bidirectional connection initiation

Both peers may establish the authenticated session:

- agent-initiated connections cover laptops, dynamic addresses, and networks
  where only outbound access is reliable;
- central-initiated connections cover stable LAN nodes and measure whether
  pull-style availability is operationally useful; and
- after authentication, both directions carry the same duplex protocol. The
  initiator does not gain different replication authority or semantics.

The designated master keeps a roster of node identities and optional endpoints.
Every joined node knows the master's identity and endpoint. LAN discovery may
locate the master, but the transport never depends on discovery after joining.

Simultaneous connections are expected, not treated as an error. After mutual
authentication, both sides compare stable node identities and a connection
nonce using one deterministic tie-break, retain one session, and close the
other. Cursors, credits, retries, and acknowledgements belong to the peer
identity, never to a connection instance, so changing initiation direction
cannot duplicate or lose work.

Sync uses a dedicated authenticated endpoint. The unauthenticated v0.5 web API
must not be exposed or reused as the fleet trust boundary. Credentials and
payloads are never written to ordinary logs; failed authentication is bounded,
auditable, and discloses no node inventory.

### 5.3 Local failure containment

- Sync work is bounded independently from scan, content, and interactive query
  admission.
- Central unavailability cannot create unbounded memory use or block catalog
  commits.
- Durable backlog has explicit row, byte, and age measurements and a configured
  storage ceiling with a visible degraded state; it is never silently dropped.
- A malformed or incompatible remote message fails closed for that peer without
  taking local search down.
- Disabling sync leaves the local source authoritative and searchable.

## 6. Content and chunking bakeoff

Metadata fleet search is the release floor. Content transfer is an experimental
vertical slice whose strategy is selected by measurement, not by making every
candidate a permanent storage or wire-format fixture.

Two independent decisions are measured:

1. **Protocol batch framing:** row-count, byte-count, and time-bounded flushes.
2. **Content payload reuse:** whole compressed extracted content, fixed-size
   chunks, and content-defined chunks (FastCDC candidates at more than one
   target size).

Transport chunking stays separate from search's line-aware text chunks. The
benchmark adapter may rechunk the versioned content payload for transfer, but
central reconstructs the same logical extracted content and indexes it through
the normal content pipeline. Alternative benchmark strategies do not become
public schema variants unless the sprint selects them.

The bakeoff uses deterministic synthetic fixtures plus approved read-only
corpora and covers:

- identical files on different hosts;
- append and prepend edits;
- localized insertion, deletion, and replacement;
- truncation and complete rewrite;
- large text, binary rejection, sparse inputs, and already-compressed inputs;
- repeated offline edits before one catch-up; and
- interrupted transfer followed by resume.

For every strategy record:

- source bytes, compressed bytes, and bytes transferred;
- reused versus novel chunk bytes;
- hashing, chunking, compression, staging, and apply CPU time;
- peak working set and durable staging size;
- chunks and protocol frames per logical version;
- time from local publication to central search visibility; and
- recovery bytes and time after interruption.

The benchmark produces a machine-readable report and a short decision record.
The release either selects one bounded strategy or ships metadata-only fleet
sync with content explicitly reported as `ContentNotReplicated`. Ambiguous
results do not justify carrying several production strategies.

## 7. Observation and instrumentation

The product emits protocol-level measurements because the observatory cannot
infer causality from system I/O alone:

- per-peer connection attempts, successful direction, duration, and reason for
  disconnect;
- source head, offered, applied, acknowledged, and compacted sequences;
- backlog rows, bytes, and oldest age;
- batch materialization, network, durable-apply, projection, and total
  search-visible latency;
- retry, duplicate, overlap, fence, full-resync, and Merkle-repair counts;
- bytes by message family and credits in use; and
- central ingest and projection queue depth.

The observatory schema gains a distinct `Collector` process class. Classification
must identify the running collector by its own process identity rather than by
the shared `eidos.exe` filename. ETW access by the core remains `Indexer`, while
collector access and spool traffic become `Collector`. Existing collector
resource samples remain the exact measure of the observer's own CPU, memory,
handles, threads, and I/O.

Every host records a standalone baseline before synchronization is enabled.
The same workload is then measured with sync enabled so observer cost, local
indexer cost, and incremental fleet cost can be separated.

## 8. Work sequence

The sequence is gate-driven; later work does not compensate for a failed
earlier invariant.

### Track A: contract and unified setup

- Record the experimental fleet boundary, identity, authentication, endpoint,
  session tie-break, version negotiation, and retirement semantics in an ADR.
- Add the advanced collector option to the guided setup while retaining two
  runtime services and data roots.
- Give the core and collector one coordinated numeric release version.
- Extend installer CI across core-only, core-plus-collector, upgrade from the
  separate collector package, repair, uninstall-with-data, and explicit purge.

Gate: one setup installs a healthy standalone core with or without a healthy
collector, and every lifecycle path preserves or removes exactly the state it
claims.

### Track B: source and central storage adapters

- Adapt the catalog sync ledger to the `eidos-sync` durable storage seams.
- Implement consistent materialization from real source rows.
- Implement central replicated-source tables and atomic effect/watermark apply.
- Project remote changes through the existing incremental search follower.
- Expose per-source central coverage, epoch, cursor, and freshness.

Gate: an in-process real-SQLite adapter test reproduces the protocol simulator's
duplicate, crash, rewind, epoch, compaction, and repair cases.

### Track C: authenticated duplex transport

- Define versioned framing, size limits, feature negotiation, and deadlines.
- Provision a stable node identity and per-node credential through manual
  enrollment.
- Implement agent connector, central connector, and listeners for both peers.
- Implement deterministic duplicate-session resolution and bounded reconnect.
- Keep the existing web API on loopback unless separately and explicitly
  configured; it is not a sync endpoint.

Gate: either side can establish the only surviving session, direction can
change across reconnects, and all durability behavior is identical in both
directions.

### Track D: fleet search and content experiment

- Make remote metadata searchable in the central service with truthful host,
  source, freshness, and completeness fields.
- Run the batch-framing and content-chunking bakeoffs.
- Select and document one content strategy, or deliberately ship metadata-only
  replication with explicit content incompleteness.
- Add the protocol metrics and distinct collector process class.

Gate: central metadata searches agree with the union of the participating
local catalogs at their acknowledged watermarks; any missing content is
reported rather than silently omitted.

### Track E: private-fleet soak and release

- Establish a sync-off baseline on the central, one stable workstation, and one
  intermittently connected machine.
- Enable the fleet path and run normal work with the collector active.
- Exercise the failure matrix in Section 9.
- Resolve every release-blocking result or record an explicit scope reduction.
- Run the complete Windows, installer, signing, upgrade, and release-candidate
  checks.
- Publish signed v0.5.0 assets and checksums.

Gate: the release definition in Section 11 is satisfied.

## 9. Required failure and compatibility matrix

At minimum, automated integration tests or recorded private-fleet exercises
must cover:

| Scenario | Required result |
|---|---|
| Agent offline for at least 72 hours | Local work continues; bounded catch-up converges without a recrawl when retained history permits |
| Central stops before apply commit | No effect or watermark becomes visible |
| Central stops after commit but before ACK | Duplicate resend is idempotent and eventually acknowledged |
| Agent stops with unacknowledged work | Durable backlog resumes from the same epoch and cursor |
| Both peers initiate simultaneously | Exactly one authenticated session survives; progress does not reset |
| Connection direction changes | The same peer cursor resumes without duplicate source registration |
| Duplicate, overlapping, delayed, and reordered frames | Central converges or fences according to the existing protocol |
| Journal replacement or deliberate source rebuild | A new epoch forces the defined full-source path |
| Same-epoch rewind/restore | Central fences the source and exposes an actionable alarm |
| Retained suffix no longer covers central | Merkle repair changes only divergent leaves and handles authoritative absence |
| Central is unavailable during heavy local churn | Local query and indexing remain healthy; backlog stays within its configured bound |
| Old/new protocol versions meet | Negotiated compatibility succeeds or the peer fails closed without data loss |
| Core or collector is upgraded while busy | Both services stop promptly, restart cleanly, and retain identities and cursors |

Synthetic tests remain authoritative for destructive fault injection. Private
corpora are read-only and are never modified to manufacture a failure.

## 10. Explicit non-goals

The following remain after v0.5:

- automatic node or central discovery;
- polished enrollment, credential rotation, retirement, and reassignment UI;
- more than one central, central replication, failover, or high availability;
- peer-to-peer search or multi-writer source ownership;
- remote file open, download, or desktop-action routing;
- WAN relay, NAT traversal, or dependence on inbound reachability;
- fleet policy orchestration and source leases UI;
- final bandwidth/storage optimization beyond the measured chunking choice;
- macOS/Linux fleet parity;
- multi-user authorization; and
- a promise that the experimental fleet wire protocol is stable beyond its
  explicit version negotiation contract.

## 11. v0.5 release gates

### Correctness and durability

- All existing standalone tests remain green.
- The real catalog/storage adapters pass the protocol's crash, replay,
  duplicate, fencing, compaction, and repair semantics.
- A central search at an acknowledged watermark matches the union of the
  corresponding local metadata images.
- No node reports complete fleet content coverage for content that was not
  replicated and indexed centrally.
- Local search remains available throughout central failure and reconnect.

### Security and privacy

- Every sync session mutually authenticates stable peer identities.
- The dedicated sync endpoint enforces bounded frames, deadlines, and peer
  admission before processing payloads.
- The existing unauthenticated web API remains loopback-only by default.
- Credentials, raw content, paths beyond the core product's catalog contract,
  and study keys do not appear in ordinary or installer logs.
- Collector data retains its SYSTEM/Administrators-only ACL and its privacy
  inspector continues to enumerate the exact exported schema.

### Performance and operability

- Backlog memory is bounded and durable disk growth is measured under the
  longest exercised disconnection.
- Sync cannot starve interactive search, local ingest, or clean shutdown.
- Local metadata and content query p95 retain the existing v0.5 absolute gates
  with sync enabled and regress no more than 15 percent from the recorded
  sync-off baseline on the same host and corpus.
- Central sustained apply capacity is at least five times the fleet's measured
  aggregate peak arrival rate, and the 72-hour offline exercise drains faster
  than new work arrives until it converges.
- Encoded and decoded frame limits, per-peer in-flight byte credits, and durable
  staging ceilings are fixed before the private-fleet soak; exceeding one
  produces backpressure or a visible degraded state, never an allocation based
  only on a peer-declared size.
- Catch-up, central apply, projection lag, bandwidth, CPU, and storage
  amplification are recorded for each dogfood host.
- The chunking bakeoff produces a reproducible report and one documented
  release decision.
- Status surfaces identify connection direction, peer, source cursors,
  backlog, freshness, last error, and any fence or repair state.

### Packaging and lifecycle

- The unified setup installs core-only and core-plus-collector configurations.
- A previously separate collector installation upgrades into the unified
  release without rotating its study key or losing its spool/configuration.
- Core, collector, and enrolled-node identity survive repair and in-place
  upgrade.
- Uninstall defaults preserve user indexes and collector study data; explicit
  purge removes only the requested product's data.
- The exact release candidate passes clean install, start, status, search,
  stop, restart, busy upgrade, repair, uninstall, and reinstall on Windows.

### Release mechanics

- `Cargo.toml` carries numeric release version `0.5.0`, not `0.5.0-dev`.
- Windows format, lint, full tests, sync simulation soak, web tests/build, and
  installer lifecycle workflows pass on the release commit.
- The manual signing rehearsal succeeds before the tag is created.
- The executable, underlying MSIs, Burn engine, unified setup, and published
  checksums are signed or generated and then independently verified.
- `v0.5.0` is tagged from the tested commit; the GitHub release publishes the
  unified setup, administrator artifacts, checksums, release notes, known
  limits, and rollback instructions.

## 12. Definition of shipped

v0.5 is shipped only when all of the following are true:

1. A new Windows machine can use one signed setup to install Eidos and
   optionally its profiling collector.
2. A standalone installation remains a complete and supported topology.
3. At least two enrolled Windows nodes synchronize real local metadata with
   the manually configured central, with successful sessions initiated in
   each direction.
4. Central search returns the acknowledged union with truthful offline,
   freshness, and content-completeness reporting.
5. The required failure matrix has current evidence from the release candidate.
6. The profiling comparison separates core, collector, and incremental sync
   cost and records enough evidence to accept or revise the central-agent
   architecture.
7. The chunking bakeoff has produced a decision; unresolved content strategy
   results in an explicit metadata-only boundary rather than multiple permanent
   implementations.
8. Install, upgrade, rollback, and uninstall preserve the states they promise.
9. Signed `v0.5.0` artifacts and checksums are publicly available with the
   experimental fleet boundary stated in the release notes.

Failure to meet a fleet gate does not justify weakening local correctness. The
permitted scope reduction is to ship the same unified installer and standalone
product with fleet synchronization disabled and clearly document the failed
gate. It is not permissible to advertise partial or unauthenticated multi-node
behavior as complete.
